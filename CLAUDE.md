# SOC Agent — Guía para agentes

Plataforma Flask de threat intelligence para analistas SOC. 20 APIs de threat intel + Tavily (OSINT web) + 5 LLMs con routing. Entry point real: `wsgi.py` (no hay `run.py`).

## Comandos

```bash
# Tests (requiere Postgres local con BD soc_agent_test)
python -m pytest tests/unit -q          # suite completa (~375 tests, ~90s)
python -m pytest tests/unit/test_X.py -q  # un módulo

# App en desarrollo
flask run --debug                        # el CLI de Flask auto-carga .env
```

En scripts sueltos de Python, `.env` NO se auto-carga: usa `from dotenv import load_dotenv; load_dotenv('.env')` antes de `create_app`.

## Base de datos — Alembic

Migraciones en `migrations/versions/` (Flask-Migrate). Al cambiar un modelo:

```bash
flask db migrate -m "descripcion corta"   # autogenerate contra soc_agent (dev)
# revisar SIEMPRE el archivo generado en migrations/versions/ antes de aplicar
flask db upgrade                           # aplica a soc_agent (dev)
```

`soc_agent_test` en teoría no necesita el `ALTER TABLE`/migración manual porque `tests/unit/conftest.py` llama `db.create_all()` en cada corrida — pero **eso solo crea tablas que no existen**, nunca agrega columnas a una tabla ya existente. Si algún flujo (CI, u otro agente "espejando CI exacto") corre `flask db downgrade base && flask db upgrade head` contra `soc_agent_test`, esa BD también queda 100% gobernada por las migraciones — cualquier columna que no esté en `migrations/versions/` desaparece igual que en dev. Ya pasó una vez (columna `crtsh_data` agregada solo con `ALTER TABLE` manual, sin migración → un downgrade+upgrade de espejo-CI la borró de `soc_agent_test` y rompió 47 tests reproduciblemente). **Tratar siempre `soc_agent_test` como si estuviera sujeta a `flask db upgrade`, nunca asumir que el `create_all()` de conftest la salva.**

`autogenerate` no ordena bien tablas con FK circulares (ver `incidents`/`investigation_sessions` en la migración base) ni detecta objetos que no son metadata de modelos (extensiones como `pg_trgm`) — revisar el diff generado, no aplicarlo a ciegas. Además, la baseline (`b9a306dbac54`) tiene drift real contra la BD viva: pedirle `flask db migrate` hoy genera decenas de cambios no relacionados (borra índices GIN legítimos como `idx_censys_data`/`idx_ioc_value_trgm`, degrada JSONB→JSON en las tablas `mitre_*`, etc.). **Regla dura: si agregaste una columna con `ALTER TABLE` manual (o cualquier cambio de esquema fuera de Alembic), escribe tú mismo un archivo de migración mínimo a mano en `migrations/versions/`** (`down_revision` = la head actual, un solo `op.add_column(...)`/`op.drop_column(...)`) — no uses el autogenerate para eso, arrastra todo el drift de arriba. Verifica el archivo de verdad: dropea la columna, corre `flask db upgrade` contra dev **y** contra test (`FLASK_ENV=testing flask db upgrade`), confirma que la recrea, antes de darlo por bueno. Los `.sql` sueltos en `migrations/` (fuera de `versions/`) son historial pre-Alembic, ya no se ejecutan desde ningún lado (ver `migrations/LEGACY_SQL.md`).

En Windows con Postgres en español, agrega `?client_encoding=utf8` a la URL de psycopg2 o los errores de conexión dan `UnicodeDecodeError`.

## Convenciones obligatorias

- **Lista de APIs**: nunca hardcodear listas de nombres de APIs — usar `IOCAnalysis.api_source_names()` (derivada de las columnas `*_data` del modelo). Una API nueva = una columna `<nombre>_data` + cliente + entrada en `_is_api_compatible` + despacho en `async_executor._resolve_method`.
- **`risk_level`**: grafía canónica `CRÍTICO` (con tilde), garantizada por `@validates` en `IOCAnalysis`. No escribir filtros duales `in_(['CRÍTICO','CRITICO'])`.
- **Errores 500**: usar `safe_error_response(e, "contexto")` de `app/utils/responses.py`. No repetir el bloque `if current_app.debug` inline.
- **Auditoría**: `AuditEvent.log(...)` NO commitea por defecto. En rutas terminales (donde no hay commit posterior) pasar `_commit=True` o el evento se pierde.
- **Visibilidad de incidentes**: usar `Incident.is_visible_to(user)` / `Incident.visible_to(user)` / `Incident.visibility_criterion(user)`. No reimplementar la regla admin/creador/asignado.
- **Frontend**: `escapeHtml()` está definida UNA vez en `base.html` — usarla siempre al interpolar datos de APIs/LLM en `innerHTML`; no redefinirla por template.
- **CSP estricta (ALTO-11)**: `script-src` usa nonce + `strict-dynamic`, sin `'unsafe-inline'`. Todo `<script>` lleva `nonce="{{ csp_nonce() }}"`. **Prohibidos** los handlers inline (`onclick=`, `onchange=`…) y las URLs `javascript:`: usar `data-action` / `data-change` / `data-input` / `data-enter` (+ `data-args` como JSON, en Jinja con `|tojson`) que despacha `app/static/ui-actions.js`; la función destino debe ser global (`function nombre()`). Las plantillas que no extienden `base.html` deben cargar `ui-actions.js` ellas mismas. `tests/unit/test_csp.py` lo vigila. Verificar cambios de CSP en un navegador real: la consola NO muestra las violaciones de CSP de forma fiable (usar `report-uri` o un listener de `securitypolicyviolation`).
- **CSS / Tailwind**: Tailwind está COMPILADO (`app/static/css/tailwind.css`, Tailwind 3.4.17 fijado), ya no se usa el CDN. Tras añadir/cambiar clases Tailwind en una plantilla hay que ejecutar `bash scripts/build_css.sh` y commitear el CSS (`--check` verifica que está al día; requiere Node). Las clases que JS construye CONCATENANDO cadenas no las ve el compilador: van en `safelist` de `tailwind.config.js`. `tests/unit/test_tailwind_css.py` falla si una clase de las plantillas no está compilada. Todo `<style>` lleva `nonce="{{ csp_nonce() }}"`; `style-src` NO permite `unsafe-inline` (solo `style-src-attr`, residual deliberado para los `style="..."`, que no admiten nonce). Todo recurso de CDN (`<script src>` / `<link rel=stylesheet>` a https://) lleva `integrity` + `crossorigin="anonymous"`; el hash se verifica contra DOS fuentes (API del CDN y cálculo propio) y se fija en `tests/unit/test_csp.py`. No usar `*.min.js` de jsDelivr que no exista en el paquete (los genera al vuelo y su hash puede cambiar).
- **Crear IOCs**: `IOC.get_or_create(value, ioc_type, **defaults)` (atómico, SAVEPOINT ante la carrera por `uq_ioc_value_type`). Nunca `query.first()` + `IOC(...)`.
- **Transacciones**: un servicio que persiste no debe hacer `commit()` si el llamador es dueño de una transacción mayor. `SessionManager.add_ioc_to_session` acepta `commit=False` (solo flush); el llamador lo envuelve en `db.session.begin_nested()` (SAVEPOINT) y hace el commit final.
- **Incidentes**: severidades y estados viven en `Incident.VALID_SEVERITIES` / `VALID_STATUSES`; los cambios de estado pasan por `incident.transition_to()` (máquina de estados `STATUS_TRANSITIONS`, 409 si no es válida; reabrir limpia `resolved_at`). No asignar `incident.status` directamente.
- **Scoring de riesgo**: `_calculate_enhanced_score` suma SOLO evidencia de amenaza; una API que responde "limpio" aporta 0 y una que falla NO es "limpio" (queda en `api_coverage`; sin ninguna fuente, `/analyze/enhanced` devuelve 502 y no guarda). Un cambio de scoring se mide con `scripts/baseline/` (`evaluate.py` es offline sobre respuestas reales congeladas; comparar `results.json` antes/después) y `tests/unit/test_scoring_baseline.py`.
- **Perfiles de investigación** (`InvestigationProfile`, `app/services/profile_service.py`): fijan las APIs de un tipo de IOC sin planificador LLM; se ejecutan con `profile_id` en `/analyze/enhanced`. Los nombres de API se validan contra `IOCAnalysis.api_source_names()` + `_is_api_compatible`, NUNCA con listas fijas. Los perfiles del sistema viven SOLO en `SYSTEM_PROFILES` y se siembran con `ensure_system_profiles()` (`flask profiles seed`; `docker/init_db.py` lo llama tras `upgrade()`): no sembrar en migraciones. Un análisis hecho con perfil es PARCIAL (`from_profile=True`): la caché (`get_cached_analysis`) nunca lo sirve a un análisis normal, ni tras borrar el perfil (por eso `from_profile` además de `profile_id`, que pasa a NULL). `profile_id` está en `OWNER_SCOPED` de la matriz de autorización; un perfil ajeno responde 404. Un perfil de usuario se borra CON el usuario (`owner_id` ON DELETE CASCADE; con SET NULL los huérfanos colisionaban en el índice único con los del sistema).
- **CVE como tipo de IOC** (`ioc_type='cve'`, WP3): se guarda SIEMPRE en mayúsculas (`normalize_ioc_value`; el esquema y `IOC.get_or_create` lo aplican) y no es ni dominio ni indicador: en STIX es una `vulnerability`, no un `indicator`. Cuatro APIs (`nvd`, `cisa_kev`, `epss`, `exploitdb`, clientes en `app/services/cve_clients.py`) solo compatibles con `cve`. Un 200 con forma inesperada es un ERROR visible, nunca `found: False`. Exploit-DB se lee del dataset OFICIAL en GitLab (su endpoint JSON da 403 al User-Agent de la app y no se falsea). Scoring: lo que pesa es que se EXPLOTE (KEV 40, ransomware +10, EPSS, exploit público), no solo el CVSS (un 9.8 sin más señales = MEDIO). Técnicas MITRE: `cve_attack_mapper` marca la procedencia (`ctid` curado, cobertura 11 % de KEV y 0 % de 2023+; `heuristic_cvss` aproximación). Para añadir una API ya NO hay que enumerarla a mano en los constructores de `IOCAnalysis` ni en `to_dict`: se derivan de `IOCAnalysis.api_data_kwargs()` / `api_source_names()`.
- **Planificador LLM**: solo se le ofrecen las APIs compatibles con el tipo del IOC (`_is_api_compatible`); una incompatible se descarta en silencio al ejecutar y dejaba el análisis sin resultados.
- **Feeds proactivos** (WP6, `app/services/feed_{matching,sources,runner}.py`, modelos `FeedItem`/`FeedRun`/`TechStackEntry`): CVEs nuevos de CISA KEV y NVD (CVSS v3 alto/crítico) casados con el stack declarado. UN registro por CVE (`cve_id` único): un CVE ya conocido que entra en KEV se ESCALA (`escalated_at`), no se duplica. Se ejecutan con el servicio `feeds` de docker-compose (`flask feeds daemon`), NUNCA con un planificador dentro de la app (Gunicorn tiene 3 workers: se ejecutaría 3 veces) ni con Celery (3 procesos más para 2 tareas). Lo vencido sale de `feed_runs` (sobrevive a reinicios) y un `pg_advisory_lock` por fuente impide ejecuciones simultáneas. Casado: tokens, nunca subcadena (`go` no casa `google`; `log4j` sí casa `log4j2`); los CVE frescos no tienen CPE en NVD pero SÍ `affected` de la CNA, de ahí se casa. La prioridad usa `LLMOrchestrator._cve_points` (una sola definición de 'peligroso') y KEV tiene suelo ALTO. El stack es GLOBAL y solo lo edita `senior_analyst`+. Un fallo o una forma inesperada de una fuente es `FeedError` visible en `feed_runs`, nunca 'cero novedades'.
- **Fixtures con respuestas reales de terceros** (`tests/fixtures/baseline/`): se redactan ANTES de commitear con `scripts/baseline/scrub.py` (correos de personas, claves de API incrustadas en páginas de phishing, `oobCode`, valores de `set-cookie`). `collect.py` lo hace solo; un fixture nuevo capturado a mano pasa por `python scripts/baseline/scrub.py archivo`. Apareció el correo de una persona real en un snapshot ya commiteado.
- **Política de salida** (WP4, `app/utils/egress_policy.py`): un IOC interno (IP privada/loopback/link-local incluida 169.254.169.254, host de URL con esas IP o codificada como `127.1`/`0x7f.0.0.1`/`2130706433`, `localhost`, nombres de una sola etiqueta y sufijos `.local .lan .internal .corp .home .intranet .private .localdomain .home.arpa`, más `EGRESS_INTERNAL_DOMAINS`) o con formato que no es el de su tipo NO sale a ninguna API de terceros: `evaluate`/`enforce` (ALLOW/DENY; MASK solo para texto libre vía `mask_text`; REQUIRE_APPROVAL RESERVADO y sin usar). Una sola definición de 'interno'. Se aplica en 5 sitios: `analyze_with_intelligence` (choke de análisis, chat y profundo), `execute_apis_parallel` (defensa en profundidad, falla cerrado), validación temprana en `/analyze/enhanced` y `/deep/analyze` (422 antes de caché/BD), `sanitize_llm_prompt` (enmascara el texto libre antes del LLM/Tavily) y el chat (`_egress_refusal`: el IOC lo decide el MODELO, se valida igual que uno tecleado). Cada DENY deja `AuditEvent('egress_denied')`; ALLOW no se audita. Antes la regla de IPs privadas solo existía en `validate_ioc` y la ruta principal y el chat dejaban salir internos a hasta 10 terceros. Una nueva llamada a `requests.*` directa (fuera de `http_client`) esquiva el punto único: un test lo vigila. Límite: un dominio interno con nombre público hay que declararlo.
- **Telegram** (WP7 v1, SOLO avisos salientes de los feeds; `app/services/telegram_client.py` + `feed_notifier.py`): el token del bot viaja DENTRO de la URL y aparece COMPLETO en el texto de cualquier excepción de red (probado): todo lo que sale del módulo pasa por `redact()` y `TelegramError` solo se construye con texto redactado; no hay librería, solo `http_post`. Solo se envía a `TELEGRAM_ALERT_CHAT_IDS` (lista permitida), solo info pública de CVE (Telegram es un tercero sin cifrado de extremo a extremo) y el texto de NVD/KEV se escapa (HTML). Sin token Y chats no hace nada. `FeedItem.notified_at` NULL = pendiente; se marca solo si ≥1 chat lo recibió y ninguno falló de forma transitoria (un fallo permanente, p. ej. bot bloqueado, no bloquea al resto); escalar a KEV lo vuelve a dejar pendiente; ventana `TELEGRAM_BACKLOG_DAYS` para no inundar con histórico. El daemon avisa en cada ciclo (`maybe_notify`, con espera de 10 min tras un fallo). `flask telegram test` es la verificación REAL (sin ella el WP no está 'hecho'). Comandos entrantes (/analizar, /feed) NO están: exigen vincular chat↔usuario, servicio aparte y refactor de la ruta de análisis.
- **Cadena de auditoría** (WP1, `app/services/audit_chain.py`): cada `AuditEvent` se SELLA AL INSERTAR (`before_flush`, bajo `pg_advisory_xact_lock`) con `HMAC-SHA256(AUDIT_CHAIN_KEY, canónico(fila)+prev_hash+posición)`; el hash cubre todas las columnas salvo `id` y `user_id` (la FK `ON DELETE SET NULL` lo cambia: `username` es su copia). Clave OBLIGATORIA en producción (`ProductionConfig.init_app`), fuera de la BD y de sus backups; sin ella (dev/test) es SHA-256 simple y solo detecta ediciones torpes. Con clave, una fila `key_id='none'` o de clave desconocida es ROTURA (no 'no verificable': un atacante podría forjarla); rotación: claves viejas en `AUDIT_CHAIN_PREVIOUS_KEYS`. El trigger `audit_events_guard` bloquea DELETE y UPDATE (salvo `user_id`→NULL y sellar legado); es defensa en profundidad, la barrera es el HMAC. LÍMITES: quien tiene la clave falsifica la cadena, y truncar la cola solo lo detecta el ANCLA (el daemon la publica por Telegram cada 24 h; `flask audit verify --anchor POS:HASH`). Todo `AuditEvent.log` debe comitear enseguida (`_commit=True`): el bloqueo dura hasta el fin de la transacción (`TestGuardaDeContencion` lista las 4 excepciones conocidas). Si cambias el canónico, sube `algo` (el sellado no se recalcula). Legado: `flask audit seal-legacy` una vez. NUNCA `DELETE`/`UPDATE` sobre `audit_events` en código ni en tests (usa TRUNCATE).
- **Roles de BD y compose** (prelaunch-report-3): la app y el daemon `feeds` se conectan como `APP_DB_USER` (`soc_app`: NOSUPERUSER, no dueño de las tablas, sin DELETE sobre `audit_events`, sin acceso a `alembic_version`); solo `app` recibe al administrador (`MIGRATION_DATABASE_URL`) y solo para que `docker/init_db.py` migre y llame a `app/utils/db_roles.ensure_app_role` (idempotente, en cada arranque). Motivo: `soc_admin` es SUPERUSUARIO en la imagen de Postgres y con él una inyección SQL apagaría el trigger de auditoría. `POSTGRES_PASSWORD` y `APP_DB_PASSWORD` son obligatorias (`${VAR:?}`, sin valor por defecto). Compose interpola desde el entorno o `.env`, NO desde `env_file: .env.docker` (esa variable solo llega al contenedor): definirlas allí las ignoraba en silencio. `raw_connection()` es del pool y el autocommit PERSISTE: restaurarlo antes de `close()`.
- **Backup/restore** (`scripts/ops/`): `backup_db.sh` escribe en `.partial` y solo renombra si el dump está COMPLETO (gzip íntegro + marca final `PostgreSQL database dump complete`; un dump cortado pasaba `gzip -t`), con permisos 0600/0700 y `--no-acl`. `restore_db.sh`: `psql` con `ON_ERROR_STOP=1 --single-transaction` (un error deshace todo y no imprime éxito), exige gzip, cabecera Y marca final antes de tocar nada, exige parar `app` y `feeds`, y quita `GRANT/REVOKE/ALTER DEFAULT PRIVILEGES` FUERA de los bloques COPY (una fila de datos puede empezar por `GRANT `): en un VPS/volumen NUEVO el rol `soc_app` no existe y esos GRANT abortaban todo el restore; los privilegios los repone `docker/init_db.py` al arrancar `app`. Los respaldos NO salen del servidor: copiarlos fuera, cifrados. Nunca `gzip | head | grep -q` con `pipefail` (SIGPIPE rechazaba volcados reales >4 KB; lo destapó verify_docker). `DB_CONTAINER` permite probarlos contra un stack aislado.
- **Secretos en texto** (`app/utils/secret_redaction.py`, prelaunch-report-4 A2/A3): el texto de una excepción de `requests` lleva la URL COMPLETA con la clave de la API si viaja en la query (Shodan, Pulsedive, Safe Browsing, IPinfo, IPGeolocation): los clientes lo devolvían en `{'error': str(e)}` y acababa en logs, BD (`*_data`), JSON, exports y prompts de LLM. `http_client` re-lanza las excepciones ya redactadas (mismo tipo, `from None`), `SecretRedactingFilter` filtra los handlers (y los loggers de urllib3, que imprimen la URL al reintentar) y Sentry usa lo mismo. Redacta el VALOR de cada secreto configurado (variable de entorno/config que acabe en `_KEY/_TOKEN/_SECRET/_PASSWORD/_DSN`), el token de Telegram, `key=/token=/apikey=` en queries, `Bearer` y la clave de una URL `usuario:clave@`. **TODA llamada HTTP pasa por `http_client`** (un test lo vigila, sin excepciones). **Sentry** se inicia SOLO con `sentry_init_kwargs`: `before_breadcrumb` + `before_send` + `before_send_transaction` (las transacciones, 5 % de muestreo, llevaban las claves en los spans) y `include_local_variables=False`; los nombres de clave se juzgan por PATRÓN (`Auth-Key` de abuse.ch y `X-OTX-API-KEY` de OTX no coincidían por igualdad).
- **Sonda de salud y `ALLOWED_HOSTS`**: el HEALTHCHECK consulta `127.0.0.1:5000`; con un dominio real en `ALLOWED_HOSTS` recibía 400 (app unhealthy, `feeds` sin arrancar). `register_host_validation` acepta Host de loopback SOLO si el cliente TCP real también lo es (se mira el anterior a ProxyFix: un `X-Forwarded-For` falsificado no sirve). No hace falta poner `127.0.0.1` en `ALLOWED_HOSTS`.
- **Clave de la cadena perdida**: `AUDIT_CHAIN_LOST_KEY_IDS=<key_id>:<última_posición>` (solo enlace, no contenido) y `AUDIT_CHAIN_ACCEPT_UNKEYED=<última_posición>`: el TOPE es obligatorio (una entrada sin él se ignora, `true` ya no vale). Sin tope, una inyección SQL con INSERT podía añadir filas con el `key_id` (público) de la clave perdida y la cadena seguía 'íntegra'. `flask audit verify` sugiere el tope (primer tramo contiguo) pero el operador DEBE confirmarlo con sus anclas. `AUDIT_CHAIN_PREVIOUS_KEYS` para rotar. Procedimiento en `docs/runbooks/RUNBOOK-AUDIT-CHAIN.md`.
- **Despliegue** (prelaunch-report-4): `app` ejecuta `env -u MIGRATION_DATABASE_URL gunicorn` (el administrador no queda en el entorno del proceso web); Redis exige `REDIS_PASSWORD` (la caché usa pickle: acceso a Redis = ejecución de código) y va en `REDIS_URL`; `feeds` lleva `init: true` (sin init el daemon, PID 1 sin manejador de SIGTERM, moría con SIGKILL, exit 137) y `app` NO: con init el PID 1 es tini, que conserva el entorno ORIGINAL (con `MIGRATION_DATABASE_URL`) legible en `/proc/1/environ` y anularía el `env -u`; `stop_grace_period` en ambos; `HEALTHCHECK --start-period=90s`. Migraciones a mano: `docker exec soc-agent sh -c 'DATABASE_URL="$MIGRATION_DATABASE_URL" flask db upgrade'` (el entorno de `docker exec` es el del contenedor, no el de gunicorn).
- **Codigo con barras invertidas desde el shell**: la herramienta de shell convierte secuencias como `\n` o `\b` en caracteres reales (un salto de linea, un backspace invisible) dentro de heredocs `python - <<EOF`, y rompio literales y rutas de Windows. Para escribir codigo con escapes usar Write/Edit, o rutas con barras normales.
- **Sin mocks en `app/`**: nunca importar `unittest.mock` ni detectar `Mock` en runtime; los tests parchean `requests.get/post` (ver fixture `_http_session_via_requests` en `conftest.py`).
- **Auth**: el logout es solo `POST` con `csrf_token` (nunca un enlace GET). El login hace un hash de relleno si el usuario no existe (igualar tiempos) y bloquea la cuenta tras 5 fallos/15 min (`app/utils/login_throttle.py`, cuenta por nombre intentado, exista o no). El desbloqueo manual es `unlock_account()` (añade un evento `account_unlocked` que reinicia el contador; NUNCA borrar los `login_failed`, la auditoría es de solo inserción): API `/api/v2/admin/accounts/unlock` + página `/admin/accounts` (solo admin) y, si el propio admin queda bloqueado, `flask accounts unlock <usuario>`. La cabecera `Host` se valida contra `ALLOWED_HOSTS` (`app/utils/hosts.py`): en producción tras un proxy con dominio propio hay que definirlo o todo da 400.
- **Dependencias**: antes de dar por buena una versión, probar una instalación LIMPIA (`python -m venv` + `pip install -r requirements.txt`), no solo el entorno conda: ya ocultó que SQLAlchemy 2.1 rompe `postgresql://` (psycopg v3) y que faltaba `tzdata`. `SQLAlchemy<2.1` es un tope obligatorio. Verificar CVEs contra OSV, no solo con informes.
- **Docker**: antes de dar por bueno un cambio de despliegue, `bash scripts/ops/verify_docker.sh` (levanta un stack aislado `socverify` en el puerto 5071 sin secretos, ejecuta 82 comprobaciones (incluye backup+restore reales, restore en volumen nuevo, rol sin privilegios, Redis con contraseña, arranque con dominio real en ALLOWED_HOSTS) y lo destruye). No hay otra forma de saber que el contenedor arranca: `python docker/init_db.py` necesita `PYTHONPATH=/app` y ya estuvo roto sin que ningún test lo viera. Los `.sh`/`Dockerfile`/`.yml` van con LF (`.gitattributes`). La capacidad de Gunicorn `gthread` NO es workers×hilos: depende del reparto de conexiones entre workers (ver bitácora); un reverse proxy con buffering es la defensa contra clientes lentos.
- **PDF/DOCX (ReportLab)**: `Paragraph(...)` interpreta marcado HTML y **hace la petición HTTP de `<img src>`** al renderizar (SSRF ciego, verificado; `rl_config.trustedHosts` NO lo evita en 4.1.0). Todo texto no confiable (LLM, valor de IOC, título de sesión, MITRE, datos de APIs) pasa por `esc()` de `app/utils/pdf_safe.py` antes de ir a un `Paragraph`; para python-docx usar `plain()`. `tests/unit/test_prelaunch2_fixes.py` lo prueba con un servidor local que registra visitas.
- **Acceso a objetos**: el acceso a un `IOCAnalysis` pasa por `authorized_analysis()` (`app/utils/analysis_access.py`), nunca por copias del `if user_id != ...`. `tests/unit/test_authz_matrix.py` descubre las rutas con `<int:session_id|incident_id|analysis_id>` y prueba 4 actores no dueños: una ruta nueva con parámetros sin clasificar hace fallar el test (hay que decidir su política en `OWNER_SCOPED`/`GLOBAL_PARAMS`).
